The dial tone was a promise you could hear: pick up the phone, and it works, anywhere, without you understanding a thing about how. The API is the same promise, made to developers instead of callers — call this endpoint, and a phone network’s deepest capability answers, without you needing a telco degree. This essay is about how that happened, and the standards quietly doing the heavy lifting.

## CPaaS was the gateway drug

The first taste was communications. **CPaaS** — a Communications Platform as a Service — turned sending an SMS or placing a call into an API request. A `POST`, and a device on the other side of the planet buzzes. **RCS** is now upgrading that plain SMS into something richer — verified senders, media, read receipts — the texting experience finally catching up to the apps.

It’s genuinely magical, and — because I worked close to this — I’ll tell you the unglamorous half too. The moment a capability is callable, it’s abusable. “SMS pumping” (also called artificially inflated traffic) is a fraud where bots trigger floods of verification texts to numbers that quietly earn the fraudster a cut. Every beautiful API has a shadow like this, and handling it is most of the real work.

## From messaging to the network itself

The bigger shift is that the *network’s own* capabilities are now becoming APIs — not just messaging bolted on top.

Through **CAMARA** (an open-source project under the Linux Foundation, backed by the GSMA) and the **GSMA Open Gateway** initiative rolling it out across operators, you can now call things that used to be locked deep inside the network:

- **Number Verification** — confirm a user controls a phone number, silently, without an SMS code.
- **SIM Swap** — check whether a number’s SIM was changed recently (a classic account-takeover signal).
- **Device Location** — a network-verified location, harder to spoof than GPS.
- **Quality-on-Demand** — ask the network for a guaranteed level of service for a window of time.

Sit with that. A capability that used to require a bespoke integration with each operator becomes a documented API call. That is the whole revolution in one sentence.

## The mess the standards are cleaning up

Here’s the problem standards exist to solve. Without them, every developer times every operator is a fresh, custom integration — an **N×M** explosion of one-off connections that never scales. A shared standard collapses that into *one contract many operators honour* — exactly what SS7 did for calls a century ago, now for capabilities.

That’s why this era has a whole alphabet working underneath it:

- **OpenAPI** — the standard way to *describe* a REST API precisely, so it can be documented, generated, tested, and governed. The contract.
- **AsyncAPI** — OpenAPI’s event-driven twin, for the streams and webhooks that IoT and real-time telecom run on.
- **TM Forum Open APIs** — standard interfaces for the business and operational guts of a telco (billing, ordering, inventory).
- **3GPP network exposure (the NEF)** — the part of the mobile-network architecture whose *job* is to safely expose internal capabilities outward.

None of these is glamorous. All of them are the reason any of this works across companies that compete.

## And then there’s IoT

The other half of programmable telecom is the machines. Billions of devices — sensors, trackers, meters — connect over telco-grade IoT (NB-IoT, LTE-M), increasingly with **eSIM/iSIM** so a SIM is a piece of software you provision remotely, not a card someone posts to you. Connectivity itself becomes an API: activate a fleet, set a data policy, watch usage — programmatically, at scale, over event streams.

- **The good:** you can manage a million devices like you manage a cloud service.
- **The bad:** a long tail of cheap, rarely-updated devices is a security nightmare, and “manage a million things” is a genuinely hard operational problem.

## The honest ledger

Where the programmable network stands today, without the hype:

- **The good:** telco superpowers democratised; composable building blocks; entirely new products (fraud checks, on-demand quality, silent verification) that were previously impossible for ordinary developers.
- **The bad:** decades of legacy to drag along; uneven rollout, so an API that works on one operator may not on the next; real questions about whether developers will *pay* for network features; and a security surface that grows with every endpoint.

That last one is not a footnote — it’s the whole next essay. The network learned to talk, then handed developers its powers.
