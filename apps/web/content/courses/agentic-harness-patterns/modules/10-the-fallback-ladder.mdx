<LearningObjectives>
- Design an ordered list of fallbacks for a failing agent step
- Distinguish errors worth retrying from errors that are not

### The problem

Every pattern so far can say no: the gateway refuses, a breaker opens, the governor stops the run. Each of those needs an answer to "then what?" If the answer is "an error page," the harness protects you and hurts the user.

The **Fallback Ladder** is a planned sequence of progressively simpler ways to still be useful. You decide the order in advance, calmly, instead of improvising during an outage.

### Try it

### The rungs

1. **Primary:** the best model with full tools
2. **Retry with backoff:** for temporary errors only (timeouts, rate limits, 5xx)
3. **Secondary provider:** a different provider's model. This is why the repo routes every call through the LLM gateway and does not hard-code one vendor
4. **Smaller model or cached answer:** worse, but still an answer
5. **Graceful refusal and a human:** say what happened and who will follow up. This rung has no dependencies, so it cannot fail

### Retry only what is worth retrying

| Error | Retry? |
|---|---|
| Timeout, 429, 500, 503 | Yes, with backoff |
| 400 bad request, schema error | No. Retrying repeats the mistake |
| 401 or 403 | No. Fix the credential |
| Content refusal from the model | No. Change the request or escalate |

### Implementation

```python
import random, time

class Retryable(Exception): pass

def with_backoff(fn, tries=3, base=0.5):
    for n in range(tries):
        try:
            return fn()
        except Retryable:
            if n == tries - 1:
                raise
            time.sleep(base * 2 ** n + random.random() * 0.1)   # jitter

def answer(question, providers, cache):
    for name, call in providers:                # ordered: primary, secondary, small
        try:
            return {"text": with_backoff(lambda: call(question)), "via": name}
        except Retryable:
            continue                             # next rung
    if question in cache:
        return {"text": cache[question], "via": "cache"}
    return {
        "text": "I cannot answer this right now. A person has been notified and will reply by tomorrow.",
        "via": "human_handoff",
    }
```

Each rung records `via` in the [trace](/courses/agentic-harness-patterns/07-the-trace-pipeline). Watching how often traffic lands below rung 1 is one of the best health signals you have. Pair each rung with its own [circuit breaker](/courses/agentic-harness-patterns/05-the-circuit-breaker) so a dead rung is skipped instantly.

<Callout type="important" title="Tell the user what they got">
A degraded answer presented as a full one is worse than an honest one. If the answer came from the cache or a smaller model, say so in a line. Trust survives "this may be a bit less detailed than usual." It does not survive being quietly wrong.
</Callout>

### Putting the ten together

<Diagram title="One request through the whole harness">

```
  request
     │
  Context Boundary ──► label and filter inputs
     │
  agent loop ◄─────────── Cost and Rate Governor (budget, steps)
     │
  Tool Gateway ──► Permission Boundary ──► Approval Gate
     │                                        │
     ▼                                        ▼
  Sandboxed Runtime / real tools       human decides
     │
  Circuit Breaker on each dependency
     │
  Fallback Ladder if anything above fails
     │
  every step ──► Trace Pipeline ──► Shadow Evaluation Harness (before the next release)
```

</Diagram>

The ten patterns are not a checklist to complete in one go. Start with the gateway and the trace, because they make everything else possible. Add the governor before your first long-running agent. Add the rest as the agent gains more power. The wider argument is in [Harness Engineering](/courses/harness-engineering); the day-to-day practice of running it is in [AI Ops](/courses/ai-ops).

<ChapterSummary>
- Plan the degradation order in advance, ending in a rung that cannot fail
- Retry only temporary errors, with backoff and jitter
- Route across providers through one gateway so a vendor outage is a rung, not an outage
- Record which rung answered, and tell the user when the answer is degraded
</ChapterSummary>
